# Design notes

Notes for picking this project up and carrying on. The README says *what* is here; these notes say *why* it is the way it is and *what to do next*.
Read these notes before you resume work.

Last updated: 2026-11-17

---

## 1. Goals and assumptions

- Use aluminium extrusion like a DIN rail, and keep adding parts, one per device, that hold Raspberry Pis, mini PCs, network routers, power strips and so on side by side.
- The extrusions are 20x20 and 40x40 (6 mm slot, 2 mm lip, 12 mm under the lips, 6 mm slot depth).
- There is also a version for real DIN rail (TS35 x 7.5, EN 60715: 35 mm wide, 7.5 mm deep, 1 mm sheet). It also fits aluminium TS35 rails 7.3 mm deep with 1.5 mm side walls.
- **The back of the frame is assumed to be blocked.** Shapes that wrap around from the back cannot be used.
- The frame normally runs horizontally (as a rail). Mounting on a vertical frame has not been tested with the current one-piece design.
- Printed on an FDM printer without supports. Assumed conditions: 256 mm square build plate, 0.4 mm nozzle, PETG.

## 3. Output format (keep it the same every time)

- **One model per file.** Output 3MF, STL and STEP.
- 3MF and STL files are in print orientation, centred on a 256 mm square build plate: upright brackets with the board plate down, flat and shelf brackets on their side with the board plate standing up. The grip is always on the build plate.
- File names are `<board>_<2020|4040|DIN35>[_<orientation>][_spacer]`. `<board>` is the name of the board's definition in `boards/` (`PiB.json` -> `PiB`): `PiB`, `PiA`, `PiZero`, `VIM1S`, `ROCK5B`, `BBB`, `M2`, `LP3Delta`, `MuLite`, `N2Plus`, `M1`, `OPi5Pro`, `OPi5`, `OPi5Plus`, `OrinNano`, `NanoKVMDesk` or `NanoKVMLite`. `<orientation>` is `upright-landscape`, `flat-portrait`, `flat-landscape`, `shelf-portrait` or `shelf-landscape`; upright portrait has no suffix, so the original file names did not change. `_spacer` (integrated standoffs) exists for the upright orientations only. A board held in a cradle also has `<board>_cradle`, the same for every bracket of that board (history 20).
- **Generated files are not committed** (`/models/` is in `.gitignore`). Pushing a `v*` tag makes `.github/workflows/build.yml` build every model with `--check` and the coupons, put each board's 3MF, STL and STEP files into `<board>.zip` (in a folder named after the board), and attach the zips, `viewer.html` and the coupons to that release. It stops if a file in `models/` would not be in the release. It uploads to a draft first and publishes it once every file is up, so `releases/latest` never points at a release with only some of the files. The job uploads only the files the release is still missing and tries up to four times 10 minutes apart (GitHub's secondary rate limit stopped uploads of several hundred files part way before the zips), and a re-run of the job picks up where it stopped. Push the next `v0.x.0` tag on `main` after each merged change to the models, the README's download links or the viewer (section 2).
- The README links to `https://github.com/koedame/sbc-frame-brackets/releases/latest/download/<board>.zip`, which follows the latest release. Keep board names and file names stable: renaming a board breaks its link, and people look for a file in the zip by its name.
- A release holds at most 1000 files. With one zip per board there are 24 (17 zips, `viewer.html` and 6 coupons) for 408 models and one cradle in 3 formats, and each new board adds one. The workflow still stops before uploading if there are more than 1000.
- `build_all.py` builds only what is asked for (`--board`, `--mount`, `--orient`, `--format`), so a change to one board does not need a full build.
- `viewer.html` embeds three.js and opens without a network connection.
- `viewer.html` includes the full three.js MIT license (`vendor/LICENSE-three.txt`) as an HTML comment, so the notice is not lost when `viewer.html` is copied on its own.

## 4. History (rejected ideas and why)

Kept so the same ideas are not proposed again.

### History 1: choosing from four mounting methods → dropped

At first the mounting method was chosen by conditions from four options: snap-fit, slide-in from the end, clamp-around and twist-lock.
When the frame is used like a DIN rail, the value is that every device goes on and comes off the same way. A different method per device throws that away, so a single mounting method was chosen.

### History 2: two-part design (A/B standard) → dropped

A standard was designed with a frame-side part A (fixed shape) and a device-side part B (designed per device), with B sliding down into A.

- In the dovetail version, the upper edge of the groove in part A started in mid-air, so it could not be printed without supports.
- The printability check at the time only looked at face angles, missed this and wrongly reported "no supports needed" (fixed in the check method in section 6).
- Switching to a 45-degree French cleat made it printable, but nothing stopped it from coming out: it lifted off when pulled forward.
- On the maintainer's suggestion it became one piece. The print orientation of the L (front plate down) matches that of the grip (rail direction up), so a single part prints without trouble.

**Limits of the one-piece design**: the device cannot be removed on its own. Each frame size needs a separate part. Devices whose print orientation does not match the grip (flat parts you would want to print lying down) may not work as one piece.

### History 3: how the grip evolved

| Version | How it grips | Result |
|---|---|---|
| Top: rigid hook, bottom: spring clip | The top takes the weight | Made identical top and bottom after the maintainer pointed it out |
| Identical flexible hooks top and bottom (8 mm to the back plate) | Hooks set 8 mm forward to gain flex length | Tightened up after the maintainer pointed it out |
| Folded spring (3 mm to the back plate) | Hooks folded back along the back of the back plate | **Too loose in a test print; did not stay on** |
| No gap, stiff arms (current) | The back of the back plate sits directly on the frame front | Weak engagement in a test print → barb raised to 1.0 mm |

- The key that sits in the front slot was added on the maintainer's suggestion. The key takes the vertical load, and the hooks only keep the bracket from coming off.
- Raising the barb to 1.0 mm increases how far the arms open, so the arms were tapered from 1.6 mm at the root to 0.9 mm at the tip. A rough beam calculation gives about 3.1% strain and about 61 N push-on force per arm.

### History 4: adding the DIN rail version

The same front plate as the frame version, with a grip for DIN rail.

- **The frame grip cannot be reused**: the rail lips are thin and shallow (1 mm), so arms coming straight off the back plate cannot get enough flex length (the strain is far too high).
- **Leaf springs**: the hooks sit at the tips of cantilevered leaf springs that run along the rail (the print height direction). The leaf springs are cut free from the back plate by a gap on each side (0.5 mm inside, 1.5 mm outside) and joined only by the 3 mm on the build plate side. The band of back plate in front of each spring is cut free with it and moves with it. They flex vertically (x), so they print in the same orientation.
- **Centre key**: sits in the rail channel (between the side walls). It was meant to take the vertical load rigidly, like the key in the front slot of the frame version, but the roots of the leaf springs touch the lip edges first and take it (below); the key is the back-up. The hooks on the leaf springs keep the bracket from coming off.
  - **23.6 mm wide since 2026-11-17** (`DIN_KEY_HALF` 11.8, was 12.2), so it fits aluminium rails with 1.5 mm side walls (24 mm channel, 0.2 mm to spare on each side) as well as steel rails with 1 mm sheet (25 mm channel, 0.7 mm on each side, was 0.3 mm). `--check` checks every DIN model against both rails (section 6).
  - The wider clearance on steel rails does not add vertical play. The 3 mm at the root of each leaf spring is part of the solid back plate and sits 0.05 mm (`DIN_FIT`) from the lip edge, so it touches the lip edge long before the key touches a side wall, on either rail. That was already so with the 24.4 mm key, so in practice the roots of the leaf springs take the vertical load and the key is the back-up.
- **How this differs from the "spring structure with a gap" avoided earlier**: what was avoided was a gap between the back plate and the frame, which caused play. The back plate of the DIN version sits directly on the rail front; the only gaps are beside the leaf springs.
- **Outer gap 2.0 mm (2026-11-15).** The outer gap used to be 0.5 mm, but the barb tip has to move 0.75 mm (`DIN_HOOK` − `DIN_FIT`) to clear the lip edge. The band in front of the spring would have hit the back plate with the barb still 0.25 mm on the lip, so the bracket could neither be pushed on nor levered off (moving the spring and band 0.75 mm outwards overlapped the back plate by 9.75 mm3; the overlap starts at 0.5 mm).
  - The spring bends rather than moving as a whole. The lip edge pushes it at the lowest point of the barb tip (where the 45-degree underside ends), and the spring stays straight above that point, so its top end (z = 8 mm) moves further than the barb tip. With the 7 mm hook of the time that point was z ≈ 1.8 mm, 6.8 mm above the root at the top of the front plate, and the top end moved 1.77 mm by beam theory, 1.63 mm at the band and 1.75 mm at the spring behind it (where nothing is in the way) by a linear FEA of the spring and band. Hence 2.0 mm rather than 1.0 mm.
  - The back plate beyond the outer gap stops the spring a little after the barb clears, so it cannot be bent much further than pushing on needs. The inner gap stays 0.5 mm: the spring moves away from it.
  - `--check` now moves each spring, its barb and its band outwards by the beam estimate (`din_spring_travel()`) and reports the overlap with the rest of the bracket, which must be 0. This is on the safe side: the real spring moves less near its root.
- **Strain at the root of the leaf springs lowered (2026-11-17).** With a 7 mm hook (`DIN_NOSE_H`) and a 1.2 mm spring (`DIN_LEAF_T`), the bending strain at the root came to about 2.9% (cantilever 6.8 mm to the lowest point of the barb tip, 0.75 mm deflection; the FEA gave 2.85%), with about 13.5 N per spring to bend it that far and about 11 N of push per spring before friction. (The estimate before 2026-11-15, 1.7% and 4.8 N, took the load at the middle of the barb.)
  - The spring runs along the print height, so it bends across the layers. Bambu Lab's PETG Basic data sheet (V3.0) gives 2550 MPa and 35 MPa across the layers (Z), so it starts to yield at roughly 35 / 2550 ≈ 1.37%. Covestro's *Snap-Fit Joints for Plastics* design guide allows 0.7 times the yield strain for a part snapped on once (0.96% here) and 0.6 times that again for one taken off and put back repeatedly (0.58%). 2.9% was about three times the first, so the roots would likely have whitened or cracked.
  - The strain is ε = 3·δ·t / (2·a²), δ = 0.75 mm (`DIN_HOOK` − `DIN_FIT`), t = spring thickness, a = root to the lowest point of the barb tip. The ways down, by beam theory:

    | Change | a (mm) | Strain |
    |---|---|---|
    | 7.0 mm hook, 1.2 mm spring (until 2026-11-17) | 6.81 | 2.91% |
    | Shorter hook at the tip end (4.0 / 3.0 / 2.0 mm) | 9.81 / 10.81 / 11.81 | 1.40 / 1.16 / 0.97% |
    | Thinner spring (0.8 mm) | 6.81 | 1.94% |
    | Shallower hook (`DIN_HOOK` 0.55) | 6.56 | 2.09% |
    | **3.0 mm hook and 0.8 mm spring (adopted)** | **10.81** | **0.77%** |
    | 2.0 mm hook and 0.8 mm spring | 11.81 | 0.65% |

  - **Adopted: a 3.0 mm hook kept at the tip end of the spring and a 0.8 mm spring** (the maintainer's choice: the first that comes under 0.96%). 0.77% by beam theory, 0.75% by the FEA (largest at the root). It takes about 1.1 N per spring to bend it that far (FEA; 1.09 N by beam theory) and about 0.9 N of push per spring before friction (the lead-in face of the barb is about 40 degrees from the push direction).
  - What it costs: the spring is about 12 times softer, so each barb is pressed behind its lip by about 1 N instead of 13.5 N, and the hook catches the lip over 3 mm instead of 7 mm (moved 0.3 mm forward, a bracket overlaps a steel rail by 0.96 mm3 instead of 2.46 mm3). The catch face is square to the pull, so a straight pull does not lift the barb; `--check` still finds the bracket held forward, up and down on both rails. For a given strain the force grows with a³, so a short hook as far out as it goes is the best case: under 0.96% no combination gets much more than about 2.7 N per spring by beam theory (a 2.0 mm hook with a 1.19 mm spring).
  - **Outer gap 1.5 mm (2026-11-17).** The top end of the softer, longer spring only has to move 0.98 mm to clear the lip (beam theory; 0.95 mm at the band and 0.99 mm at the spring behind it by the FEA), so the 2.0 mm gap would have let it bend twice as far as pushing on needs, to about 1.6% at the root, past yield. At 1.5 mm the stop comes at about 1.2%, under yield, and the band still has 0.5 mm to spare (the 2.0 mm gap left 0.23 mm). The narrower spring and gap make the back plate 0.9 mm narrower on each side of the grip and lower the shelf on DIN rail by 0.9 mm; the beam estimates of the DIN versions (history 8) change by at most 0.3 mm and 0.02 MPa (`OrinNano` flat landscape bends 0.3 mm less, the flat orientations start a little closer to the grip).
  - Not tried on a print: whether the roots whiten, how firmly the softer springs hold, and how easily the bracket pushes on (section 9).

### History 5: shorter print time (version 1 → 2)

| Change | Effect on time (estimate) |
|---|---|
| Remove the bosses (standoffs) | The largest. Many layers of small circles |
| Make the back plate a low rim on the outer parts | About −1% |
| Fewer cross ribs | About −3% (not adopted, it reduces stiffness) |

- Most of the time goes into printing walls; removing volume does not save much time.
- The number of layers is set by the width along the rail (16 mm). Making it narrower reduces the engagement of the hooks and the key, so it was left alone.

### History 6: the whole Raspberry Pi range (2026-11-15)

The maintainer asked for brackets for every Raspberry Pi, and for STL files as well.

- **One bracket per board size**, not one per model. Boards with the same outline and mounting holes on their official drawings would get identical files under different names, so they share one: the former `Pi4` became `PiB` (Raspberry Pi 5 / 4 B / 3 B+ / 3 B / 2 B / 1 B+), and `PiA` was added for the 3 A+ / 1 A+. `PiZero` covers the Zero, Zero W and Zero 2 W. The geometry of `PiB` is unchanged from `Pi4` (same volumes).
- `PiA` follows `PiZero` (one hole set that fits either way round, SD notches at both ends, two windows) with the window band of `PiB` (clear of the 6 mm standoffs).
- **Not covered**: Raspberry Pi 1 Model A / B (no official mechanical drawing, so the holes cannot be checked), Compute Modules (they need a carrier board), Raspberry Pi 400 / 500 (keyboard computers), Raspberry Pi Pico (a microcontroller board).
- STL files are written next to 3MF and STEP, with the same placement as the 3MF and the same tessellation (0.02 mm, 0.2 rad). About 270 KB each.

### History 7: popular boards from other manufacturers (2026-11-15)

The maintainer asked for popular boards from other manufacturers, in the same vertical orientation as the Raspberry Pi brackets, with STL files too.

- **Existing brackets first.** A board whose outline and mounting holes match an existing bracket on its official drawing or 3D model gets no new files, only its name in the class title and the README: Radxa ROCK 3C and Pine64 ROCK64 → `PiB`, Radxa ZERO 3W / 3E → `PiZero`, Khadas VIM3 / VIM4 → `VIM1S`.
- **The VIM3 uses the `VIM1S` bracket.** A first survey said one VIM3 hole differs (53.5 mm where the VIM1S has 45.5 mm). On the official DXF and 3D model the holes are identical to the VIM1S; the 53.5 mm is measured from the board edge to the far hole, not between holes.
- **ZERO 3W / 3E**: the holes on the official DXF are up to 0.14 mm away from the Raspberry Pi Zero positions (3.55 / 3.6 / 61.4 mm along the board and 3.6 / 26.45 / 26.5 mm across, against 3.5 / 61.5 and 3.5 / 26.5). The board holes are 2.8 mm, so an M2.5 screw still has 0.15 mm of play on each side and reaches the `PiZero` standoffs. The DXF puts the holes on a layer named `PIN_TOP`; the official 3D models confirm they are the mounting holes (through the PCB at the same positions).
- **`--board-step` replaces `--vim1s-step`.** Each board class lists the official 3D models it fits in `STEPS` (rotation, centre of the PCB outline and height of its underside, in the file's own coordinates), and `sbc_brackets.official()` places any of them on its bracket. The placement was checked by comparing the holes in each model with the bracket holes: VIM3 / VIM4 exact, ZERO 3W / 3E within 0.14 mm, ROCK 5B / 5B+ within 0.06 mm. The VIM1S result is unchanged from before.
- **Models that are partly surfaces.** The ROCK 5B+ model (its PCB among others) and parts of the VIM1S / VIM4 / ZERO models are shells that belong to no solid. `--check` counts their area that lies strictly inside the bracket (faces lying on the bracket's surface, such as the board resting on the standoffs, are not counted).
- **ZERO 3E**: the pads under the holes stand 0.02 mm proud of the PCB underside in the official model, so its underside height in `STEPS` is the pad level (otherwise the pads overlap the standoff tops by 1.30 mm3).
- **ROCK 5B / 5B+ get their own bracket (`ROCK5B`).** 100.2 x 74.25 mm, four 3.5 mm holes 93.15 x 49 mm apart, 3.55 mm from the GPIO-side edge (the survey had guessed 58 x 49 mm).
  - Standoffs are 8 mm: the deepest parts under the ROCK 5B+ reach 5.4 mm below the board, and the ROCK 5B's microSD card sits under it. An SSD fitted in the M.2 slots under the board is not in the official models and has not been checked.
  - Standoffs are 5.4 mm in diameter, M2.5 with a 2.2 mm pilot hole. A part under the 5B+ is 3.1 mm from a hole centre; a 7 mm standoff overlapped it.
  - Board holes in the version without standoffs are 3 mm, as on the other brackets.
  - No SD notch: the microSD slot is at the GPIO-side edge on the underside. The ROCK 5B's card (in its official model) sticks out 9.8 mm past that edge, above the front plate and beside the frame; on the 40x40 version it clears the slope of the back plate by 0.42 mm. The ROCK 5B+ model has no card in the slot; its slot is in the same place, so the card should sit the same way, but this has not been checked against a model.
  - Two rows of lightening windows, clear of the standoffs.
- **Not added**: Libre Computer AML-S905X-CC (Le Potato). Its product page gives 85 x 56 mm and holes 58 x 49 mm but not their distance from the edges; it has not been checked against the official 3D model yet (added in history 11). The ROCK 3C and ROCK64 have no official 3D model, so only their outline, holes and microSD position were compared on the drawings.

### History 8: six orientations and release files (2026-11-15)

The maintainer asked for five more orientations next to the original one, for every board and mount: upright landscape, and flat and shelf, each in portrait and landscape.
The grip had to stay as it is, every model had to print without supports and clear the frame and the board placed in its orientation, and the existing file names had to stay.

- **The grip stays on the build plate.** It only prints one way up, so every orientation keeps the grip where it is and changes how the board plate sits relative to it. Holes, openings, standoffs, the simplified board and the official 3D models are defined once, on the upright-portrait plate (the "board frame"), and `place()` moves them to the orientation. The grip is the same in all six, so all of them can be mounted upside down.
- **Upright landscape**: the board plate still lies on the build plate, with the long side pointing away from the frame. The microSD end of the Raspberry Pi and ZERO boards (`SD_END`) faces the frame, so the gap to the back plate is 17 mm there (`SD_GAP`) for a finger to reach the card, instead of 4 mm.
- **Flat**: the back plate itself becomes the board plate, and the board sits in front of it beside the grip. On DIN rail the board moves further along the rail when one of its holes would reach the gap that a leaf spring needs above its free end (`flat_edge()`).
- **Shelf**: a shelf on top of the back plate, level with the top of the grip, with a gusset under its root and a rib along it. On DIN rail it is raised to clear the leaf springs' slits (`shelf_top()`). In shelf portrait the microSD end faces the frame with the 17 mm gap.
- **Standing board plates (flat and shelf).** The plate prints standing up, so the holes are teardrops (point up), every opening gets a 45-degree roof (`_vopen()`), and only the top corners are rounded. Each opening keeps the rest of its rectangle as a 1 mm pocket in the face under the board (`POCKET`): parts under the ZERO 3E reach 0.64 mm into the plate where the roof of its microSD-end notch would leave material.
- **Elephant's-foot chamfer only under vertical walls.** `bed_chamfer()` used to chamfer the whole outline on the build plate. On a standing plate some edges on the plate meet a face that leans outwards, and a chamfer there makes an overhang, so those edges are skipped.
- **No integrated standoffs on standing plates.** A standoff that sticks out sideways from a standing plate is a horizontal cantilever. Two versions were tried and dropped:
  - A teardrop boss (point down) with a thin 45-degree web under it. Printable, but the web hit parts under the ZERO 3E (2.24 mm3) and the VIM1S (about 6 mm3) in the official models.
  - A teardrop boss whose underside rises at 45 degrees from the plate. Printable and clear of the boards, but the slope eats the face the board sits on: 38% of the full ring is left on `PiB`, 19% on `VIM1S` and 73% on `PiZero`, the pilot hole is open underneath near the top, and the 8 mm `ROCK5B` standoffs run out at 6.5 mm and never reach the board.
  - So flat and shelf come only without standoffs (`SPACER_ORIENTS`; `bracket()` refuses `spacer=True` for them). The upright orientations keep both versions.
- **Release files instead of committed models (maintainer's decision).** Six orientations made 180 models at first (120 after dropping the standoffs above), 3 files each. Committing them would add every regenerated file to the history again. The outputs (3MF, STL, STEP, `viewer.html` and the coupons) are now attached to GitHub releases by CI when a version tag is pushed, and `models/` is no longer in the repository (section 3).
  - Users should not have to build anything to get an existing model. The maintainer measured the build on 2026-11-15: for the 30 upright-portrait models, 854 MB of dependencies, 23 s to install and 46 s to build, so all six orientations take about 5 minutes. People who only want a file download it from the release; only people who change a shape build, and `build_all.py` builds just the boards, mounts, orientations and formats they ask for (`--board`, `--mount`, `--orient`, `--format`).
  - The README links point at `releases/latest/download/<file name>`, so they stay the same from release to release. Since history 17 they point at one zip per board.
  - A release is published only when the maintainer asks for it.

**Using each orientation.** Edges of a Raspberry Pi B or A+ board (microSD at one short end, USB and Ethernet at the other). Upside down, top and bottom swap.

| Orientation | microSD end | Other short end | GPIO edge | Power and HDMI edge | Rail length used (`PiB`, 20x20) |
|---|---|---|---|---|---|
| Upright, portrait | Top | Bottom | Towards the frame (4 mm) | Forward | 16 mm |
| Upright, landscape | Towards the frame (17 mm) | Forward | Bottom | Top | 16 mm |
| Flat, portrait | Top | Bottom | Far side along the rail | Grip side | 72 mm |
| Flat, landscape | Grip side | Far side along the rail | Top | Bottom | 101 mm |
| Shelf, portrait | Towards the frame (17 mm) | Forward | Far side along the rail | Grip side | 56 mm |
| Shelf, landscape | Grip side | Far side along the rail | Towards the frame (4 mm) | Forward | 85 mm |

- The VIM1S / VIM3 / VIM4 have their microSD slot under the board in the middle of the power and HDMI edge. The ROCK 5B / 5B+ have it under the board at the GPIO edge, and the ROCK 5B's card sticks out 9.8 mm past that edge.
- In shelf landscape the GPIO edge is 4 mm from the frame, so a HAT or a ribbon cable may not fit. In upright portrait the GPIO edge faces the frame too, as before.
- Upside down, a shelf bracket hangs the board below the shelf from its four screws.
- In the flat orientations the board's components face away from the frame; in the shelf orientations they face up.

**Beam estimates for the long overhangs.** Each bracket without standoffs was sliced every 0.5 mm along its overhang, and the deflection at the far edge of the board and the peak bending stress were integrated with the unit-load method from the second moment of area of each slice. The board's own stiffness is ignored (it stiffens the plate in reality), and so are stress concentrations at the corners of the openings. Material: Bambu Lab PETG Basic data sheet V3.0, 2780 MPa and 51 MPa along the layers (XY), 2550 MPa and 35 MPa across them (Z). Flat plates bend across the layers; upright and shelf plates bend along them.

- **The board's own weight is no problem.** With 1 N (about 100 g) at the board centre, every orientation stays within 0.8 mm and 2.2 MPa. The weight lies in the plate's plane in the upright and flat orientations (negligible), and across the shelf in the shelf orientations.
- **A 10 N push at the far edge of the board**, roughly what plugging in a cable takes, bends the long overhangs a lot:

| Bracket (20x20) | Upright portrait, side push | Upright landscape, side push | Flat portrait, pull out | Flat landscape, pull out | Shelf portrait, push down | Shelf landscape, push down |

### History 9: BeagleBoard.org BeagleBone Black (2026-11-16)

The maintainer asked for a BeagleBone Black bracket in all six orientations.

- **Sources.** BeagleBoard.org publishes no 3D model or DXF of the board, but its design files are public. Links in section 7.
- **Outline 86.36 x 54.61 mm (3.400 x 2.150 in).** The text of the System Reference Manual says "3.5” x 2.15” (86.36mm x 53.34mm)". Its own dimension drawing and the manufacturing data both give 3.400 x 2.150 in, so the 3.5 in and the 53.34 mm in that line are wrong. The corners have a 0.25 in radius at the Ethernet end and a 0.5 in radius at the microSD end. PCB 0.062 in.

The Rev D change notice describes electrical changes and calls the new microSD holder mechanically compatible, and the holes are part of the cape outline, so the Rev C3 data is used.

Every setup needs power and most need Ethernet, so the microSD end is the one that faces the frame in upright landscape and shelf portrait, with the 17 mm gap. A USB-A or micro HDMI plug does not fit in that gap; the README says so.
- **Parts under the board.** The bill of materials gives the heights of the top parts (RJ45 13.3 mm, power jack 11 mm, USB-A 7 mm, expansion headers 8.5 mm with 3.0 mm tails, which reach 1.43 mm below the board), and the footprint name of the microSD holder gives 1.8 mm. The heights of the micro HDMI and the mini USB are not published (the connector makers' sites could not be used), and the manual's "Max height: .187” (4.76mm)" does not say what it measures. So:
  - The plate is notched under the micro HDMI and the microSD holder, open to the microSD end so a finger reaches the card, and under the mini USB, open to the Ethernet end. Two lightening windows sit between them, clear of the standoffs.
  - The simplified board shows those two connectors reaching the plate. Extended through the plate (upright) or 0.99 mm into it (flat and shelf, just inside the `POCKET` depth), they stay clear of the plate in every orientation but flat landscape. There the outer 4 mm of the micro HDMI is over the rib that every flat bracket keeps above the grip (38 mm3 of overlap), so in that orientation the micro HDMI has to stand less than 6 mm below the board.
  - Standoffs 6 mm tall, above the 4.76 mm whatever it measures, and 6 mm across: the nearest parts under the board (a 0402 capacitor in the placement list, and the header pins in the drill file) are 5.2 mm from a hole centre. M3 with a 2.6 mm pilot hole (the ratio of the M2.5 and M2 pilot holes).
- **Corners.** The plate keeps the usual 3.5 mm corner radius. At the microSD end, where the board's corners have a 12.7 mm radius, the plate's rounded corners reach up to 3.8 mm past the board's along the diagonal (1.2 mm at the Ethernet end).
- **Simplified board.** Placed from the silkscreen outlines, the header pins in the drill file and the heights in the bill of materials. It is the only interference check: there is no official 3D model to pass with `--board-step`. The board design files are published without a license file (the OSHWA certificate US000236 lists the hardware license as "Other"), so, as for the other boards, nothing taken from them is distributed: no files, and no shapes converted from them in `viewer.html`.

### History 14: boards as data, and a Claude skill (2026-11-16)

The maintainer asked for boards to be added without touching the code, so that the project can be handed out as a Claude skill that builds a bracket for a board it does not have yet.

- **One JSON definition per board in `boards/`** (fields in `boards/README.md`). The board classes in `sbc_brackets.py` are gone: `Board` reads every file in `boards/` at import, and the file name is the board's name. A definition gives the outline, the mounting holes, the standoffs and which holes get them, the microSD edge, the openings (rectangles, and rows of windows), the simplified board as boxes, and the official 3D models it fits. What was code before is now numbers: the notch arithmetic of `PiB`, `PiA`, `PiZero`, `VIM1S` and `BBB` became plain rectangles, and the window rows (`WIN_S`, `WIN_N`) became `windows`.
- **One coordinate convention.** Before, each class had its own `xy()`, and some of them mirrored the board: those of `ROCK5B`, `BBB`, `LP3Delta`, `MuLite` and the heatsink boards, and the one `PiB` used for its holes and openings (not for its simplified board). Their shapes came out right because the holes and openings are symmetric or were entered mirrored too. Now every definition is in the board's top view, right-handed, and `frame_edge` (`s=0` or `s=S`) says which edge along `l` faces the back plate, a half turn and never a mirror. The mirrored ones were converted: `ROCK5B`, `BBB` (now the manufacturing data's own x), `LP3Delta`, `N2Plus` and `M1` by `l -> L - l`, and `MuLite` by `s -> S - s`. `SD_END` became `microsd_edge`, the edge the card comes out of; the 17 mm gap applies when that is the end that faces the frame. The `rotate` of an official model is now relative to the board's top view too (half a turn more than before for `frame_edge` `s=S`), so every model lands where it did.
- **Heights of the simplified boards count from the top of the standoffs.** For `N2Plus` and `M1` that is the underside of the heatsink's base, so their part heights are 6 mm lower than in the old `HKSink.ghost()`, which counted from the bottoms of the side walls.
- **Nothing moved.** All 264 models have the same volume (mm3, 6 decimals), bounding box and number of faces and solids as before, and so do the holes, standoffs, openings, the simplified boards in every orientation and the placement of every official model. The STEP volumes match the tables below, and `--check` passes with every official 3D model.
- **Checks on a definition.** An unknown or missing field, a hole off the board, a standoff that is not on a hole, or a box whose start is not below its end stops the build with the file and the field.
- **Viewer.** It now shows the number of standoffs and the hole diameter from the definition, instead of a fixed "× 4" and "3 mm". The models are listed in file name order, so the viewer opens on `BBB` instead of `PiB`.
- **Claude skill (`skills/sbc-frame-brackets/SKILL.md`).** For a supported board it hands over the download links from the README and builds nothing. Otherwise it takes the dimensions from the official drawing or 3D model, writes the definition, builds only the files asked for with `--check`, shows them in the viewer and hands over the 3MF, STL and STEP files.
  It was tried in a fresh `python:3.11-slim` container set up as in the README's "Building from source": following only the skill and `boards/README.md`, a made-up 70 x 50 mm board, described by a text drawing, was added and built in flat portrait for 20x20, and all 24 of its models passed `--check`. What that run found unclear (which edge `frame_edge` is, the heights of parts on top of the board, how deep a notch goes, where the full check writes its files) is now spelled out in the skill and in `boards/README.md`.

Ledges 0.8 mm wide and 5 mm long under the four corners of the board: nothing is under its long edges there (the header pins under the board end 0.95 mm in from the edge). End stops 1.6 mm thick beyond both short ends, reaching 3.45 mm in from each long edge, clear of the USB-C port and the Ethernet jack, and ending 0.1 mm below the top of the board, under the female headers and the HDMI board, which stand out past the end. A lip 6 mm long at the middle of each wall, 45 degrees above and below, reaches 0.6 mm over the board's edge onto the plastic of the 10-pin header along that edge, 2.57 mm above the board. The HDMI board ends 12.7 mm from the USB-C end of the board, so it is not above the lips. The underside of the board is 4 mm above the cradle's, and the cradle is open under the board, for the heatsink Sipeed supplies (its size is not published; 10 mm from the board's underside to the plate with the 6 mm standoffs, 13 mm at the plate's opening).
- **Snap force.** The walls bend outwards between the end stops to let the board in. Taken as a beam 1.2 x 9.6 mm over the 35.9 mm between the end stops, pushing the lip 0.6 mm out takes 2.4 N per wall if the ends were free to turn and 9.5 N if they were fixed, and strains the wall 0.34 to 0.67%, well under the 1.8% at which PETG reaches its strength (51 MPa / 2780 MPa). Not tried on a print (section 9).
- **Checked against the official 3D model.** The cradle has no overlap with the board in the 3D model, and moving the board 0.05 mm down, 0.12 mm up, 0.2 mm across or 0.25 mm along makes it overlap the ledges, the lips, the walls or the end stops, so the board is located in every direction. The cradle is symmetric, so the board goes in either way round.
- **Edges.** The USB-C port, the HDMI port and the microSD slot are at one short end. That end faces the frame in upright landscape and shelf portrait, 17 mm (`SD_GAP`) plus the cradle's 7.75 mm from the back plate to the end of the board: right-angle plugs fit there, straight ones do not (README). The microSD card goes in under the board, so it can only be changed with the board out of the cradle. In upright portrait and shelf landscape a long edge faces the frame, 4 mm plus the cradle's 1.35 mm away.
- **Standoffs.** 6 mm tall under the cradle's end plates, 9.5 mm either side of the centre line, so that the screw heads are beside a USB-C plug's overmould rather than under it. M2.5 x 8 self-tapping screws go through the 2 mm end plates into the integrated standoffs.
- **`--check` with a cradle.** `build_all.py` builds the cradle once, checks it against the board's official 3D model (or the simplified board), and checks every bracket against the board and the cradle placed on it. No overlap and no unsupported area in the cradle and all 24 models, and the DIN leaf springs bend freely in all 8 DIN models. `viewer.html` shows the cradle on each Lite bracket.
- **Beam estimates** (table in history 8). The plate is as narrow as the cradle (25.6 mm), so the long overhangs bend like those of `PiZero`: a 10 N push at the far edge gives 9.0 mm and 32.0 MPa in upright landscape and 6.3 mm and 32.1 MPa in flat landscape, 92% of the 35 MPa across the layers. The other orientations stay within 0.4 mm and 8.6 MPa. The cradle's stiffness is ignored, as the board's is.
- 408 models and one cradle, 24 release files.

## 6. Checks and caveats

- **Printability (supports needed or not)**: use `checks_print.py`. It slices the part layer by layer and checks that each layer stays within 45 degrees of the outline of the layer below. **Do not rely on face angles alone**: that misses shapes that start in mid-air (history 2).
- **Interference**: measure the volume of the intersection between the bracket and the frame, and between the bracket and the board. Use the board's official 3D model when there is one. DIN models are measured against both a steel rail (1 mm sheet, 7.5 deep) and an aluminium rail (1.5 mm side walls, 7.3 deep; `mount_frames()`), and must fit both. A board in a cradle: the cradle against the board, and the bracket against the board and the cradle (history 20).
- **Retention**: `--check` moves the bracket 0.3 mm forward, up and down and confirms it then overlaps the frame (i.e. it is hooked on), on both rails for DIN models. A model that does not is reported as `not held` (until 2026-11-17 this was done by hand).
- **Upside down**: confirm zero interference in the flipped position too.
- **DIN leaf spring travel**: `--check` moves each leaf spring outwards by as much as pushing on needs at its top end and reports the overlap with the rest of the bracket. It must be 0; otherwise the spring is stopped before the barb clears the lip (history 4).
- **Print time**: `checks_time.py` is a home-made estimate, not a slicer measurement. Use it only to compare shapes. No slicer measurements have been taken yet.
- **One solid**: `--check` also fails a model that comes out as more than one solid (a loose piece would print as a separate part).
- **Exit status**: `build_all.py --check` exits with status 1 if any model fails any of the checks above. The workflow runs `--check` on every pull request that changes the generator, and again before attaching files to a release.
- **Regression check**: after changing the script, confirm the models you did not mean to change still have the same volume (the tables at the end of these notes).

| [Takachi Electronics Enclosure FDR series drawing](https://www.takachi-el.co.jp/assets/attachments/images/din%20rail%202022-2024.pdf) (p. 14-33) | Aluminium, 7.3 deep | 27 | 1.5 | 24 (on the drawing) |

- The tolerance of the base width could not be confirmed from available documents. Annex A.3 of IEC 60715:2017 (Figures A.3 and A.4), which defines the rail profiles, is not in the [public preview](https://cdn.standards.iteh.ai/samples/23197/de6fcc085faa4dc1a9af3ef4265d161d/IEC-60715-2017.pdf). Figure 2 (TH 35), which is in the preview, gives device-side dimensions and only shows the lip thickness 1 ±0.04 and the width 35 ±0.3.
- The drawing in Weidmüller's TS 35X7.5 datasheet only gives width 35, depth 7.5 and thickness 1, not the base width.
- The 24.4 mm key of the time had 0.3 mm to spare on each side on a steel rail with 1 mm sheet, but **did not fit aluminium rails with 1.5 mm side walls (7.3 mm deep, 24 mm channel)**: overlaid on such a rail, every DIN model interfered by 10.24 mm3 (the key hit by 0.2 mm on each side). The lip edge where the hooks catch is 1 mm thick, the same as TS35 x 7.5.
- **Since 2026-11-17 the key is 23.6 mm wide and fits both** (history 4): 0.2 mm to spare on each side on aluminium, 0.7 mm on steel. `--check` measures every DIN model against both rails.

- Take dimensions for new boards from the manufacturer's official 3D model or drawing. Do not place holes from memory or guesswork: for the VIM1S, the first guess ("rectangular pattern") was wrong.
- Official 3D models and drawings are not included (`*.stp`, and `*.step` and `*.stl` at the top level, are excluded in `.gitignore`). To re-check interference, download them from the manufacturers' sites (links in the table above) and pass each with `--board-step` (unpack the Le Potato model first: `AML-S905X-CC-V1.0.stp`, and the Orange Pi 5 and 5 Plus RAR archives). The file name tells which bracket it belongs to (`official_models` in the board's definition).
- Shapes converted from the official 3D models do not go into `viewer.html` either. `--board-step` is used only for interference checks, and the boards in the viewer are bare plates, because no notice allowing redistribution of the manufacturers' CAD data could be found (Khadas as of 2026-11-14; Radxa and Pine64 as of 2026-11-15; Libre Computer as of 2026-11-16; Orange Pi as of 2026-11-17). BeagleBoard.org publishes no 3D model, and its design files have no license file (as of 2026-11-16), so only dimensions read from them are used. The LattePanda 3D models are under CC BY 3.0 and the LattePanda Mu repository under the MIT license (as of 2026-11-16), which would allow redistribution with attribution; they are kept out all the same, so every board is handled the same way.

## 10. Steps to resume work

1. Read these notes and the README, and `boards/README.md` for the board definitions.
2. Set up the environment as in the README's "Building from source" (Python 3.11–3.14, `pip install -r requirements.txt`).
3. Run `python build_all.py --check` (or only the boards, mounts and orientations you work on, with `--board`, `--mount` and `--orient`) and confirm that it exits with status 0, and that the volumes match the tables below.
4. Of the open items in section 9, check the ones that need the maintainer's decision.
5. After changes, open a pull request. The workflow checks every model again.
6. To publish the files, push the next version tag on `main` once the pull request is merged (`git tag v0.5.0 && git push origin v0.5.0`); the workflow builds every model, packs them into one zip per board and attaches the zips to that release. Then check that every file the README links to is in the release.
7. Update sections 8 and 9 and the "last updated" date of these notes.
